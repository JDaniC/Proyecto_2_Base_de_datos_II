## Alcance implementado

1. **Cliente HTTP y transporte (`Frontend/src/services/http/`):**
   - Inyección automática de token Bearer desde `TokenProvider`.
   - Generación y propagación de `X-Correlation-ID`.
   - Soporte para `Idempotency-Key` UUID estable por intención para reintentos seguros (DEC08).
   - Sanitización de autoridad en el cliente: eliminación automática de `actor`, `institucionId`, `rol` y `profesional` en cuerpos y parámetros de mutación (DEC07).
   - Traducción unificada de errores a `HttpError` compatible con `AppError`, mapeo de errores de campos y distinción de errores reintentables (`status === 503 || status === 0`).
   - Normalización de fallos de conexión / red a `503 PERSISTENCIA_NO_DISPONIBLE` con mensaje neutral.
   - Desempaquetado del sobre `{ data, meta }` conforme a la especificación OpenAPI v1.

2. **Proveedor de autenticación de ensayo (`TrialAuthProvider`):**
   - Credenciales y tokens de ensayo para las cuatro instituciones (`admin.hospital`, `admin.dental`, `admin.lab`, `admin.pediatria` y personal clínico).
   - Soporte nativo para Firebase Auth REST API (emulador o API Key) vía `fetch` sin empaquetar SDKs pesados en el cliente.
   - Validación estricta de contraseñas (mínimo 4 caracteres) y correo obligatorio.
   - Almacenamiento seguro en cliente mediante `sessionStorage` (con fallback a memoria para entornos de prueba).
   - Notificación de vencimiento / revocación de tokens vía `onTokenExpirado` al recibir HTTP 401.

3. **Repositorio de sesión HTTP (`HttpAuthRepository`):**
   - `iniciarSesion`: ejecuta `POST /api/v1/sesion` sin cuerpo y autenticado por Bearer.
   - Mapper canónico bidireccional: traduce `CENTRO_MEDICO_PEDIATRICO` del backend al alias de presentación `CENTRO_PEDIATRICO` (DEC06).
   - `obtenerSesionActual`: ejecuta `GET /api/v1/sesion`, actualiza permisos y limpia la sesión si el token fue revocado o expiró (401).
   - `cerrarSesion`: ejecuta `POST /api/v1/sesion/cierre` para revocar tokens en el servidor y limpia el estado local.
   - `obtenerCuentasDemo`: deshabilitado en modo entrega (devuelve array vacío, DEC11).

4. **Contenedor y fábrica de servicios (`serviceFactory.ts`, `ServiceContext.tsx`):**
   - En modo `api`, inyecta `HttpAuthRepository` por defecto.
   - Los módulos clínicos aún no integrados en E01 (`patientRepository`, `appointmentRepository`, `consultationRepository`, etc.) quedan protegidos por `requireApiAdapter`, lanzando `503 PERSISTENCIA_NO_DISPONIBLE: Modo API activo sin adaptador HTTP configurado... Prohibido el fallback automático a simuladores.`

5. **Resiliencia en interfaz (`LoginPage.tsx`, `AuthSessionContext.tsx`):**
   - Acceso institucional directo sin selector de institución ni motor de base de datos.
   - Preservación íntegra de credenciales en el formulario ante error 503 para permitir reintentos seguros sin reescribir información (RNF-034).
   - Mensajes específicos para 400 (validación de campos), 401 (credenciales inválidas) y 403 (cuenta inactiva o sin permisos).

6. **Proxy de desarrollo y soporte CORS (`vite.config.ts`, `crear-aplicacion-http.ts`):**
   - Proxy de desarrollo en Vite (`server` y `preview`) para redirigir peticiones `/api` hacia el backend en `http://127.0.0.1:3000`.
   - Habilitación de CORS en la aplicación HTTP de NestJS con soporte para `Authorization`, `X-Correlation-ID`, `Idempotency-Key` e `If-Match`.
